# 11. Проверки и аудиты

Проверки устроены слоями: от дешёвых (каждый push) к дорогим (по запросу). Каждый слой ловит свой класс ошибок.

| Слой | Когда | Что ловит | Инструмент |
|---|---|---|---|
| 1. `npm run check` | каждый коммит (хук) и push (CI) | синтаксис, оформление, пределы размера, небезопасный PHP, вызов внутренних функций плагина из темы, сломанное бизнес-правило, лишний вес CSS/JS и внешние запросы, ошибки shell | `tools/check.js` (глава 15) |
| 1а. Секреты | каждый коммит и push | ключи и пароли в git | gitleaks (`scan-secrets.sh`) |
| 2. Сгенерированное актуально | в составе `check` | правку прототипа без пересборки, ручную правку сгенерированного, плохие SEO-поля | сборщик + сравнение отпечатка |
| 3. Установка с нуля | каждый push, PHP 8.3 и 8.4 | сломанный деплой, импорт, зависимость от состояния | `remote.sh` в CI ×2 |
| 4. Контракт страниц | каждый push | 500, пустые страницы, потерянные мета, редиректы, разметку | `smoke.sh` + `contract.sh` |
| 4а. SEO-гейт | каждый push | нет title/description, H1 ≠ 1, битые ссылки, noindex, canonical, alt | `tools/qa/seo-gate.js` (глава 07) |
| 5. Обход в браузере | перед PR с вёрсткой | JS-ошибки, горизонтальную прокрутку, битые внутренние ссылки | `tools/qa/crawl.js` (Playwright) |
| 6. Сценарии интерфейса | перед PR с JS | меню, слайдеры, формы, cookie, тема | `tools/qa/interact.js` |
| 7. Блоки в редакторе | после изменения сборщиков или блоков | «недействительные» блоки | `tools/qa/editor-validity.js` |
| 7а. Удобство редактора | после изменения темы, блоков, editor.css | клик в абзац не доходит до текста, липкие элементы на холсте, не сохраняется заголовок | `tools/qa/editor-usability.js` |
| 8. После деплоя | каждый деплой | сайт не открылся (→ откат), ослабла защита | `smoke.sh`, `hardening-check.sh` |
| 9. Дежурная проверка | каждые 6 часов | сайт лежит | `health.yml` → Telegram |
| 10. SEO-аудит живого сайта | раз в месяц и после крупных деплоев | SEO/GEO-проблемы, скорость, доступность, 301; ухудшение с прошлого раза | `seo-audit.yml` |
| 11. Визуальное сравнение с макетом | крупные изменения вида | расхождения с дизайном | скриншоты 1280/360, светлая/тёмная, языки |

## Слой 4: контракт страниц в CI

После установки с нуля сайт поднимается встроенным сервером PHP с роутером (статические файлы — как есть,
остальное — `index.php`). Перед проверками `blog_public = 1` — проверяем как боевой (с noindex Rank Math не
выводит canonical, а robots.txt не открывает ботов ИИ).

Что проверяется (переносится в любой проект, меняются только адреса):

```bash
# 200 и маркер темы на каждом типе страниц и языке
for u in / /en/ /prices/ /services/ /services/<услуга>/ /blog/ /<статья>/ /contacts/; do
  code=$(curl -s -o /tmp/page.html -w '%{http_code}' "$B$u")
  [ "$code" = 200 ] && grep -q 'acme-header' /tmp/page.html || { echo "::error::$u → $code"; fail=1; }
done
# старый адрес → новый одним 301
got=$(curl -s -o /dev/null -w '%{http_code} %{redirect_url}' "$B$from"); [ "$got" = "301 $B$to" ]
# SEO: description ≥ 10 символов, og:image, JSON-LD — на ключевых страницах
grep -q '<meta name="description" content="[^"]\{10,\}' ; grep -q '<meta property="og:image" content="http' ; grep -q 'application/ld+json'
# локализованный title архива, sitemap_index.xml → 200, canonical страницы блога на другом языке
# GEO: llms.txt содержит разделы «## », robots.txt содержит GPTBot, на услуге есть "@type":"Service", FAQPage, BreadcrumbList,
# автор статьи — "@id": ".../#person"
# меню на языке страницы ведёт на страницы этого языка; ссылки в форме ведут на документы своего языка
# внутренние ссылки старых статей переписаны; нет картинок со старого домена
grep -i fatal /tmp/php.log && fail=1
```

Ошибки печатаются как `::error::` — GitHub показывает их в сводке запуска.

## PHPCS (в составе `npm run check`)

`phpcs.xml.dist` проверяет три группы правил:

- **безопасность и надёжность**: `WordPress.Security` (экранирование вывода, `$_GET`/`$_POST` без `wp_unslash` и
  очистки, nonce), `WordPress.DB` (запросы без `prepare`, медленные мета-запросы), `WordPress.WP` (устаревшие
  функции, перезапись глобальных переменных), `PHPCompatibilityWP` (минимальная версия PHP);
- **оформление**: `WordPress-Core` — чинит `npm run format` (phpcbf), руками не правится;
- **читаемость**: строка, длина функции и файла, вложенность, сложность (Slevomat и Generic).

Не проверяются: Yoda-условия, gettext (подписи — через строки Polylang), обязательные описания параметров.
Сгенерированные файлы данных исключены; паттерны исключены из длины строки (сохранённая разметка блоков).

- `render.php` блока WordPress подключает внутри функции, поэтому правило «перезапись глобальных переменных»
  для `blocks/*/render.php` отключено. Префикс `$acme_` всё равно обязателен — это соглашение проекта.
- Свои функции, возвращающие безопасную разметку (`acme_icon()`), перечислены в `customAutoEscapedFunctions`.
- Осознанное исключение из правила безопасности: `// phpcs:ignore Правило -- почему` (именно `--`, иначе PHPCS не
  видит причину). Пределы размера исключениями не обходят.
- Версии правил закреплены `composer.lock` проекта: `composer install`, затем `npm run check` (или `npm run
  lint:php`). Глобальная установка не нужна.

## Слой 5: обход в браузере

`QA_BASE=http://localhost:8080 node wordpress/tools/qa/crawl.js 360` (и `1280`):

- согласие cookie ставится заранее (`addInitScript`), чтобы окно не перекрывало страницу;
- обход в ширину от `/` и главных других языков по всем внутренним ссылкам;
- для каждой страницы: статус ≠ 200, `scrollWidth > ширины` (с поиском виновника — элемент, правый край
  которого за экраном и который не внутри контейнера с `overflow`), `pageerror`;
- итог: «pages: N, problems: M» и первые 30 проблем JSON-строками.

## Слой 6: сценарии интерфейса

`tools/qa/interact.js` — линейный сценарий `ok(условие, 'что проверили')` → `PASS/FAIL`:
окно cookie (первый визит, настройки, сохранение выбора в localStorage), мегаменю (открытие, фокус в
поиск, переключение раздела, поиск находит/не находит, Esc закрывает и возвращает фокус), язык, мобильное
меню, слайдеры (кнопки, счётчик), фильтры, модальные окна, переключатель темы, калькулятор, форма (ошибки
по полям, успешная отправка → запись в «Заявки»). Отправляет одну тестовую заявку — не запускать на боевом
без нужды.

## Слой 7: блоки в редакторе

`tools/qa/editor-validity.js` входит в админку, открывает в редакторе каждую страницу/запись (или список из
аргументов) и проверяет `wp.data.select('core/block-editor').getBlocks()` рекурсивно на `isValid === false`.
Выводит запись, имя блока и начало разметки. На kalaganov5: 2 233 блока на 50 страницах — 0 недействительных.

## Слой 10: SEO-аудит живого сайта

**Actions → SEO-аудит → Run workflow** (`url`, `max_pages`):

1. `tools/qa/seo-crawl.js <url> <max> report` (Node 22 + `node-html-parser`):
   - зеркала (`http://`, `www`) → одним 301 на `https://host/`; robots.txt; закрыт ли сайт ботам ИИ
     (разбор групп robots.txt); llms.txt (число ссылок); код несуществующей страницы (должен быть 404);
   - карты сайта (`sitemap_index.xml`, `sitemap.xml`, `wp-sitemap.xml`, вложенные);
   - обход: сначала карта, затем ссылки со страниц; для каждой — код, цепочка редиректов, время ответа,
     заголовки (тип, кеш, сжатие, HSTS), title, description, robots/X-Robots-Tag, canonical, hreflang, OG,
     H1–H3, картинки без alt и без размеров, число слов, типы JSON-LD, авторы в разметке, входящие ссылки;
   - старые адреса из `legacy-urls.txt`: первым шагом 301, конечный 200;
   - `summary.md`: разделы с количеством — не 200; в карте, но не 200/noindex; ссылки на редиректы;
     индексируемые не в карте; без title / > 60 символов; без description / короче 70 или длиннее 170;
     дубли title и description; H1 ≠ 1; canonical на другую страницу; нет hreflang; нет og:image; картинки
     без alt; мало текста (< 250 слов); без JSON-LD; GEO: статьи без автора-человека, внутренние без
     BreadcrumbList, «Вопросы и ответы» без FAQPage; сиротские страницы; ответ > 800 мс; без gzip/br;
     старые адреса не 301.
2. Lighthouse mobile по списку ключевых страниц (`--only-categories=performance,seo,accessibility,best-practices`),
   из полного отчёта — выжимка `lighthouse.json`: оценки, метрики (FCP, LCP, TBT, CLS, SI, TTFB),
   непройденные проверки и до 8 конкретных элементов на каждую (селектор + кусок разметки + пояснение).
3. Сводка — в `$GITHUB_STEP_SUMMARY`; отчёт — артефактом и **коммитом в ветку `seo-reports`**
   (`reports/<дата>/`, orphan-ветка создаётся при первом запуске). История аудитов хранится в git и
   сравнивается между запусками.

Как работать с отчётом: исправления кода — PR с названием «Fix issues from the <дата> SEO audit»; задачи по
текстам — в `TODO.md` с владельцем; после выкладки — повторный аудит и сравнение.

## Внешние аудиты

Сторонние аудиторы (Топвизор, ответы фрилансеров, вебмастера) — источник задач: каждую находку проверить на
сайте, подтверждённые — в код (PR) или в TODO (тексты), неподтверждённые — в TODO с пометкой «не делать,
потому что…», чтобы к ним не возвращаться.

## Ручная приёмка

Перед слиянием крупного изменения: локальный сайт или тестовый — главная и одна страница каждого типа на 360 и
1280, светлая и тёмная тема, все языки; та же страница в редакторе; форма; консоль без ошибок; Query Monitor
без PHP-предупреждений и тяжёлых запросов.
