# 13. Процесс: git, коммиты, документация, ИИ-агент

## Ветки и выкладка

```
main ──────────────●──────────────●────────▶   push в main → деплой на тестовый (автоматически)
        \         / merge PR       \            Run workflow → production (вручную, только main)
         feature/new-hero ─●─●─●    claude/seo-fixes ─●─●
                           │ push → CI
                           └ Run workflow → test (ветка) → проверка на dev.<домен>
```

1. Свежий `main` → ветка `feature/<что>` (ИИ-агент — `claude/<что>`).
2. Правка → локальный сайт (Docker) или сразу push → CI.
3. Проверить на тестовом: Actions → Деплой → ветка, `test`.
4. Pull request в `main`, зелёный CI → Merge. Тестовый обновится из `main`.
5. На боевой: Actions → Деплой → `main`, `production`, без галочек. Деплой сделает бэкап базы.
6. Сломалось на боевом — Revert слитого PR → новый PR → деплой production. Прошлая база — `~/acme-backups/`.

Один PR — одна тема (шаблон статьи, SEO-исправления по аудиту, обложки). Мелкие правки TODO/README —
отдельными коммитами.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/), по-английски:

```
feat(blog): article template from the design handoff          ← тип(область): что сделано, повелительно, ≤ 72

- Two columns: main (H1, "Published · N min", …) and a sticky right
  column from 1024 px (contents with the current section, …)    ← тело: пункты «что и зачем», перенос ~72
- datePublished / dateModified use the update date, not post_modified
- wp acme seo also deletes Rank Math sitemap cache files directly:
  invalidate_storage() left them in place under WP-CLI           ← неочевидная причина — обязательно

Co-Authored-By: …                                                ← если работал ИИ-агент
```

| Тип | Когда |
|---|---|
| `feat` | новое поведение для посетителя или владельца |
| `fix` | исправление |
| `refactor` | код меняется, поведение — нет |
| `docs`, `test`, `ci`, `build`, `chore` | документы, тесты, пайплайн, зависимости, прочее |

Область — часть проекта: `blocks`, `editor`, `seo`, `content`, `deploy`, `security`, `blog`.

- В теле — поведение и причины, а не список файлов. Числа, если они важны («pages with video scored down
  to 52 on mobile»).
- Комментарии в коде — на языке команды/владельца (в kalaganov5 — русский), идентификаторы — английские.
- Сгенерированные файлы коммитятся вместе с изменением сборщика в одном коммите.
- Перед коммитом хук запускает поиск секретов и `npm run check`; красная проверка — коммит не создаётся.
- ИИ-агент коммитит только по просьбе владельца.

## Документация проекта

`wordpress/README.md` — единственный документ и для владельца, и для разработчика. Разделы (в этом порядке):

1. Что это: таблица папок.
2. Что нужно (версии, плагины) и установка вручную.
3. Деплой: workflow, секреты (таблица), первый запуск, боевой сайт.
4. Процесс «тестовый → боевой»; что можно править на боевом; чего избегать.
5. Запуск боевого на домене (переключение папок, откат).
6. Работа в VS Code: подготовка, каждая доработка по шагам, локальный сайт, сборщики, чего не делать,
   если что-то пошло не так.
7. Редактор: как открыть шаблон, где менять заголовок, что видно меткой.
8. Разделы по функциям: меню, обложки, перелинковка, шаблон статьи, цены, перенос, кеш, аналитика, SEO,
   GEO, адреса.
9. «Как устроено и где что править» — таблица «что → где в админке».
10. Отличия от макета (и почему).
11. Обновить контент из прототипа.
12. Что проверено (числа: страниц, сценариев, блоков) и что не проверено.

Пишется для человека без опыта WordPress: путь по меню («Настройки → Сайт → Аналитика»), что будет, если
нажать, чего нельзя делать и почему.

`TODO.md` — список дел по разделам, у каждого — владелец («Владелец», «Claude»), срочное сверху, «нужен
ответ» — отдельным разделом. Выполненное удаляется.

`CLAUDE.md` в корне — правила для ИИ-агента (шаблон в каркасе): что где лежит, команды проверки, что нельзя
делать, как коммитить, где документация. Агент читает его в начале каждой сессии.

## VS Code

- `.vscode/extensions.json`: EditorConfig, Intelephense, WordPress Hooks, ShellCheck, YAML, GitHub Actions,
  GitHub Pull Requests.
- `.vscode/tasks.json`: «локальный сайт — запустить / открыть для телефона (QR) / остановить / журнал PHP»,
  «phpMyAdmin», «новый блок темы» (спрашивает имя, название, атрибуты), «собрать контент», «проверить PHP»,
  «PHPCS», «проверить скрипты деплоя», «обход сайта 360 px».
- `.vscode/acme.code-snippets` — сниппеты проекта (префикс `acme-`, затем Tab): `acme-section`, `acme-p`,
  `acme-lead`, `acme-buttons`, `acme-facts`, `acme-faq` — каноническая разметка core-блоков с классами проекта
  (вставленная в шаблон или паттерн, она не станет «недействительной»); `acme-block`, `acme-render`, `acme-t`,
  `acme-ta`, `acme-field`, `acme-hook` — PHP; `acme-css`, `acme-mq` — правило и брейкпоинт CSS блока;
  `acme-init` — раздел `site.js` с `once()`.
- `.vscode/settings.json`: сгенерированные файлы исключены из поиска; `templates/*.html` — как HTML.
- `.editorconfig`: табы в теме, плагине и `.sh` (стиль WordPress), 2 пробела в `tools/**.js` и YAML, LF.
- `.gitattributes`: `*.sh`, `*.conf`, `Dockerfile` — `eol=lf` (скрипты запускаются в Linux, даже при клоне на Windows).

## Работа ИИ-агента в таком проекте

1. Прочитать `CLAUDE.md`, `wordpress/README.md`, `TODO.md`; для новой функции — найти похожую готовую и
   повторить её устройство (блок → как другой блок, команда WP-CLI → как `wp acme seo`).
2. Перед правкой — `git status` и ветка; не работать в `main`.
3. Менять исходник, а не результат: прототип/сборщик → пересобрать; шаблон — в `templates/*.html`, не в базе.
4. После правки — `npm run check`; для вёрстки и редактора — локальный сайт и QA-скрипты (`crawl.js`, `interact.js`,
   `editor-usability.js`).
5. Не трогать боевой сайт напрямую (SSH, SQL); всё — через деплой и админку.
6. Не запускать деплой production, `force_import`, `legacy_update` без явного «да» владельца.
7. Нет ответа в брифе, README или TODO — вопрос владельцу в формате «вопрос · варианты · влияние · рекомендация»
   (глава 15), решение — в `docs/decisions.md`.
8. В конце — коммит (по просьбе) с телом «что и почему», обновить README/TODO, если поменялось, как владелец работает
   с сайтом; в ответе — что проверено и что нет.
