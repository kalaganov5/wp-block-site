# 15. Читаемый код: правила и проверки

Цель: человек без контекста открывает любой файл проекта и понимает его за пару минут. Правила проверяет
машина (`npm run check`), а не память: то, что не проверяется, со временем перестаёт соблюдаться.

Главная задача устройства кода — **локализовать изменения**: новая функция затрагивает понятную часть
проекта, а последствия правки ловятся автоматически.

## Одна команда проверки

```bash
npm install && composer install   # один раз: линтеры (на сервер не попадают)
npm run check                     # всё сразу; так же запускают хук перед коммитом и CI
npm run check -- php js           # только названные проверки
npm run format                    # починить оформление: Prettier, Stylelint, phpcbf
```

| Проверка | Что ловит | Инструмент |
|---|---|---|
| `php`, `json` | синтаксис PHP, битый JSON | `php -l`, `JSON.parse` |
| `generated` | правку прототипа без пересборки, ручную правку сгенерированного | сборщик + сравнение отпечатка |
| `format` | оформление JS, CSS, JSON, YAML | Prettier |
| `js` | ошибки и пределы размера в JS | ESLint |
| `css` | одно объявление на строку, имена классов, вложенность | Stylelint |
| `phpcs` | безопасность, оформление, пределы размера в PHP | PHPCS: WordPress, PHPCompatibility, Slevomat |
| `boundary` | тема вызывает внутреннюю функцию плагина | `tools/check.js` |
| `tests` | сломанное бизнес-правило | `tools/tests/run.php` |
| `shell` | ошибки в скриптах деплоя | shellcheck |

Красная проверка — изменение не принимается. Локально проверка без инструмента (нет `vendor/`, нет
shellcheck) пропускается с предупреждением; в CI пропуск считается ошибкой.

Хук `.githooks/pre-commit` подключается сам при `npm install` и запускает поиск секретов в добавленных файлах
и `npm run check`.

## Пределы размера

| Что | Предел | Почему |
|---|---|---|
| Строка | 120 символов (JS — 100) | Читается без горизонтальной прокрутки, в том числе в сравнении версий на GitHub |
| Файл | 250 строк | Помещается в экран-два, читается целиком |
| Функция | 40 строк | Одна мысль на функцию |
| Вложенность | 3 уровня | Глубже — уже отдельная функция или ранний `return` |
| Сложность | 10 ветвлений | Больше — функцию невозможно проверить в уме |
| Параметры | 3, дальше — массив или объект с именованными полями | Вызов читается без подсказок редактора |

Параметры в PHP линтер не считает — это правило ревью. CSS по строкам не ограничен: его делят по блокам
(глава 02), а не по длине.

Не подпадают под пределы: сгенерированные файлы (`content/`, `strings-data.php`) и разметка Gutenberg в
`templates/`, `parts/`, `patterns/` — её пробелы и переносы являются частью сохранённого блока.

Обойти предел комментарием `phpcs:ignore` или `eslint-disable` нельзя. Исключение из правила безопасности
допустимо только с причиной: `// phpcs:ignore Правило -- почему`.

## Структура: один файл — одна задача

- Файл называется по задаче: `inc/seo/schema.php`, `inc/import/menus.php`. Папок и файлов `helpers`, `utils`,
  `common` нет: в них со временем оказывается всё подряд.
- Большая задача — папка с файлами по подзадачам, а не один файл на 600 строк.
- `functions.php` темы и главный файл плагина только подключают модули.
- **Публичный интерфейс плагина — `inc/api.php`.** Тема вызывает только функции из этого файла; всё
  остальное в плагине можно перестраивать, не разыскивая вызовы по теме. Проверка `boundary` следит за этим.
- Блок темы целиком живёт в своей папке: `block.json`, `render.php`, `style.css`.

## Имена и язык

- **Код — по-английски, всё остальное — на языке команды.** Идентификаторы английские; комментарии, README,
  названия тестов — на языке владельца проекта.
- **Словарь `docs/glossary.md`**: одно понятие — одно английское имя во всём проекте (услуга → `service`,
  заявка → `lead`). Без словаря одна сущность за месяц получает три имени.
- Имя говорит, что значение означает, а не как получено: `$contact`, а не `$c`; `remainingSlots`, а не
  `result2`. Однобуквенные имена — только счётчик цикла `$i`.
- Булевы — с `is_`, `has_`, `can_`: `$is_urgent`, `hasConsent`.
- Свои функции, классы CSS, блоки, опции — с префиксом проекта (глава 01).

## Комментарии

Комментарий объясняет **почему**, а не **что**.

```php
// Плохо: повторяет код.
// Удаляем файлы карты сайта.
foreach ( $sitemap_files as $sitemap_file ) { wp_delete_file( $sitemap_file ); }

// Хорошо: причина, которую из кода не видно.
// Из WP-CLI (другой пользователь, чем у веб-сервера) invalidate_storage() может молча
// оставить старые файлы, поэтому удаляем их сами.
```

- У каждого файла — шапка: за что он отвечает.
- Неочевидное число, порядок, приоритет хука — с причиной рядом («не ниже .85: иначе серый текст теряет
  контраст 4.5:1»).
- Закомментированный код не хранится — он есть в git.

## Принципы — с примерами из каркаса

| Принцип | Как применяется здесь |
|---|---|
| SRP — одна ответственность | Тема выводит, плагин хранит данные. Файл меняется по одной причине: `seo/robots.php` — только когда меняются правила для роботов |
| OCP — расширение без правки | Новое поле записи — строка в схеме `acme_meta_schema()`, панель в редакторе строится сама. Новый блок — папка, регистрация её находит |
| DIP — зависимость от контракта | Тема зависит от функций `api.php`, а не от опций и таблиц плагина |
| DRY — одно знание в одном месте | Цвета — `tokens.css`; «закрыта ли страница от поиска» — одна функция для robots, карты сайта и llms.txt |
| KISS — проще | Блоки без сборки: `block.json` + `render.php`; один общий `editor.js` |
| YAGNI — только нужное | Модуль переноса старого сайта не входит в каркас: он нужен не каждому проекту |

Похожий код может описывать разные правила. Объединять его только из-за внешнего сходства опасно: правка
одного правила сломает другое.

## Бизнес-правила отдельно от WordPress

Правило — то, что определяет результат для посетителя или владельца: проверка контакта в форме, подстановка
цены, транслит адреса, обрезка описания. Оно пишется **чистой функцией**: получает значения, возвращает
значение, не читает базу и не выводит разметку. Хук WordPress только вызывает её.

Такую функцию можно проверить без сайта:

```php
// wordpress/tools/tests/leads.test.php
test( 'контакт без e-mail, телефона и ника — ошибка «неверный контакт»', function () {
	$errors = acme_lead_validate( array( 'name' => 'Анна', 'contact' => 'привет' ) );
	expect_equal( 'eContactBad', $errors['contact'] );
} );
```

- Название теста — фраза на языке команды: тесты читаются как требования.
- Тест пишется до кода: сначала красный, потом правило.
- Каждая найденная ошибка в правиле становится тестом — она не вернётся.
- Запуск: `npm test` (нужен только PHP; WordPress подменён минимальными заглушками в `tests/wp-stubs.php`).

Вёрстку, шаблоны и интеграции тестами правил не покрываем — их проверяют установка с нуля и обход сайта
(глава 11).

## Вопросы по ходу работы

Если ответа нет в брифе, README или TODO, решение не принимается молча. Вопрос задаётся так:

1. **Вопрос** — одной фразой.
2. **Варианты** — два-три реальных.
3. **Влияние** каждого: что затрагивает, объём работы, что потом трудно изменить (адреса страниц, данные в
   базе, разметка сохранённых блоков).
4. **Рекомендация** — какой вариант и почему.

Принятое решение записывается в `docs/decisions.md`: дата, решение, причина, отвергнутые варианты. Через
полгода это единственный способ понять, почему сделано именно так.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/), по-английски:

```
feat(blocks): add price table with currency switch

- Prices come from wp_options so the owner edits them without a deploy
- Table collapses to cards below 600 px: horizontal scroll hid the last column
```

`feat` — новое поведение, `fix` — исправление, `refactor` — без изменения поведения, `docs`, `test`, `ci`,
`build`, `chore`. Область — часть проекта: `blocks`, `seo`, `deploy`, `content`, `editor`. Тело — что и
почему. ИИ-агент коммитит только по просьбе.
