# Сайт на WordPress: блочная тема + плагин данных + автоматизация

Версия 2.0 (история — `CHANGELOG.md`). Комплект описывает подход, на котором сделан kalaganov5.com, и даёт
каркас, чтобы повторить его на любом проекте. Всё ниже — правила, проверенные на живом сайте; причина каждого
правила записана в `references/`.

## Что получается на выходе

- **Тема** `wordpress/<slug>/` — блочная тема без сборки: `theme.json`, шаблоны `templates/*.html`,
  динамические блоки `blocks/<имя>/{block.json,render.php,style.css}`, стили на CSS-переменных, один `site.js`.
- **Плагин данных** `wordpress/<slug>-core/` — типы записей и поля, настройки сайта, импорт контента,
  SEO, формы, аналитика, безопасность, редиректы, команды `wp <prefix> …`. Тема вызывает только его публичный
  интерфейс `inc/api.php` и работает без плагина (пустые блоки, не ошибки).
- **Деплой** `wordpress/deploy/remote.sh` — один повторяемый скрипт: ставит сайт с нуля или обновляет
  тему и плагин. Его же запускают CI, локальный Docker, тестовый и боевой сервер.
- **Проверки** — одна команда `npm run check`: синтаксис, оформление, пределы размера, безопасность PHP,
  граница темы и плагина, тесты бизнес-правил, бюджет веса. Её запускают хук перед коммитом, CI и ручной деплой.
- **GitHub Actions** — `ci.yml` (`npm run check` + установка с нуля + SEO-гейт), `deploy.yml` (test/production по
  SSH, откат при сбое), `sync.yml` (копия боевого на тестовый), `health.yml` (дежурная проверка),
  `seo-audit.yml` (обход сайта + Lighthouse → ветка отчётов, раз в месяц).
- **Сборщики** `wordpress/tools/` — контент из прототипа в разметку Gutenberg, обложки, QA-скрипты.
- **Документация** — `wordpress/README.md` (для владельца сайта и разработчика), `CLAUDE.md` (для ИИ-агента), `TODO.md`,
  `docs/glossary.md` (словарь имён), `docs/decisions.md` (принятые решения).

## Главные правила (не нарушать)

1. **Код — только через git, контент — только в админке боевого сайта.** Деплой обновляет файлы темы и
   плагина и не трогает записи, меню, настройки. Копия данных идёт только боевой → тестовый.
2. **Редактор удобен владельцу.** Запись открывается без шаблона: поле заголовка (это H1) и текст, клик в любой
   абзац работает. На холсте те же стили, что на сайте, но ничто не плавает и не прилипает; шаблон — по кнопке
   «Показать шаблон». В блоках нет образцов-заглушек: пустой блок — подсказка в редакторе и пустота на сайте.
3. **Блоки темы — динамические, без сборки.** `block.json` + `render.php` + `style.css` в папке блока; панель
   настроек строит один общий `editor.js` из атрибутов `block.json`. Тексты страниц — core-блоки (абзац,
   заголовок, список, кнопки) со стилями дизайн-системы (`is-style-*`). Один H1 на странице — из шаблона.
4. **Один источник дизайна.** Цвета, шрифты, отступы — `assets/css/tokens.css` (светлая и тёмная тема);
   палитра `theme.json` совпадает с ним; свои цвета и размеры в редакторе выключены.
5. **Поля записей — без ACF.** Схема полей в PHP → `register_post_meta(show_in_rest)` → панель в
   редакторе строится по схеме.
6. **Всё повторяемо и идемпотентно.** Импорт, деплой, команды `wp <prefix> …` создают только то, чего
   нет; «перезаписать» — только явным флагом `--force`. Настройки сторонних плагинов ставятся «один раз на
   версию»: дальше главная — админка.
7. **Сгенерированное коммитится и сверяется в CI.** Если файл собирается скриптом, руками его не правят.
8. **Тестовый сайт закрыт от поисковиков и счётчиков; боевой открыт.** Это решает окружение, а не человек.
9. **Минимум плагинов.** Polylang (если языков больше одного), Contact Form 7, Rank Math, кеш страниц.
   Слайдеры, меню, cookie, калькуляторы — в теме. Никаких конструкторов страниц.
10. **Каждое правило — с причиной в комментарии.** Код и документы пишутся так, чтобы следующий
    разработчик (или ИИ) понял, почему сделано именно так.
11. **Код читается за пару минут, и это проверяет машина.** Строка ≤ 120, функция ≤ 40 строк, файл ≤ 250,
    вложенность ≤ 3; один файл — одна задача; говорящие имена по словарю; бизнес-правило — чистая функция с
    тестом. `npm run check` красный — изменение не принимается (`references/15-code-style.md`).
12. **SEO — с брифа, а не в конце.** У каждой страницы запрос, адрес, title и description в исходнике контента;
    сборщик не пропускает пустые, длинные и повторяющиеся поля; Rank Math настраивается кодом; SEO-гейт в CI
    не даёт слить страницу без title или с двумя H1.
13. **Безопасно по умолчанию.** Заголовки безопасности, закрытые XML-RPC и перечисление пользователей, запрет
    PHP в uploads, правка файлов из админки выключена, секреты не попадают в git (поиск перед коммитом и в CI),
    деплой делает бэкап базы и откатывает файлы, если сайт после выкладки не открылся.

## Как пользоваться каркасом

```bash
node ~/.claude/skills/wp-block-site/scripts/scaffold.js ../new-site \
  --slug=studio --name="Studio Pro" --domain=studio.pro
cd ../new-site && git init && npm install && composer install   # инструменты проверки и хук перед коммитом
docker compose up -d && docker compose logs -f setup              # http://localhost:8080, admin / admin
npm run check
```

`templates/project/` — рабочий проект с именем-заглушкой `acme` (тема `acme`, плагин `acme-core`,
функции `acme_*`, блоки `acme/*`, классы `acme-*`). Скрипт копирует его и заменяет имена. Без скрипта:
скопировать папку (без `node_modules` и `vendor`) и заменить `acme`/`ACME`/`Acme Site`/`acme.example` поиском по проекту.
`--force` пишет поверх, но не удаляет файлы, которых больше нет в каркасе.

Что внутри каркаса — `references/01-architecture.md`, раздел «Карта файлов».

В архиве скилла для claude.ai папки `templates/project/` нет: там не больше 200 файлов, поэтому каркас упакован в
один файл `templates/project.bundle.json` (`node scripts/bundle-template.js --zip`). `scaffold.js` разворачивает
проект и из папки, и из этого файла — результат одинаковый. Чтобы прочитать файл каркаса, разверните проект во
временную папку.

Каркас проверен (версия 2.0, WordPress 7.1.5, Rank Math 1.0.282, PHP 8.3 и 8.4): развёрнут scaffold-ом и
установлен с нуля в Docker; `npm run check` зелёный, тестов правил — 39 на PHP и 27 на JS; повторный деплой
ничего не меняет. Все типы страниц на двух языках отвечают 200, ровно один H1, 404 и 301 работают; JSON-LD по
типам страниц, карта сайта, robots.txt с ботами ИИ, llms.txt; SEO-гейт проходит и ловит удалённое описание и
второй H1. Обход 360/1280 — 0 проблем; сценарии интерфейса и редактора — PASS; блоков в редакторе — 0
недействительных; журнал PHP пуст. Защита проверена снаружи: заголовки, закрытые xmlrpc и `wp-config.php`, PHP
в uploads не выполняется, `/wp/v2/users` без входа — 401, форма работает. Откат проверен: выкладка темы с
фатальной ошибкой → страницы 500 → автоматический откат → страницы 200. shellcheck и actionlint — без замечаний.
Не проверено: запуск workflow на самом GitHub (SSH, Telegram, ветка отчётов), HSTS на живом https-сайте.

## Как передать комплект

- **Claude Code**: скопировать папку `wp-block-site` в `~/.claude/skills/` (для всех проектов) или в
  `.claude/skills/` проекта — скилл подхватится по описанию или вызовом `/wp-block-site`.
- **Другая нейросеть или разработчик**: передать папку целиком и начать с `SKILL.md`; каркас разворачивается
  `node scripts/scaffold.js` (нужен Node 22+; для проверок — Composer и Docker).
- **Публичный репозиторий**: https://github.com/kalaganov5/wp-block-site — `git clone` прямо в папку скиллов.

## Определение «готово» для любой доработки

- `npm run check` зелёный: оформление, пределы размера, PHPCS, граница темы и плагина, тесты, бюджет веса;
  сгенерированные файлы пересобраны. Новое бизнес-правило — с тестом.
- CI зелёный: установка с нуля дважды подряд (вторая — без изменений и ошибок), страницы отвечают 200, SEO-гейт пройден.
- В редакторе: запись открывается без шаблона, клик в абзац работает, на холсте ничего не плавает; блоки не
  «недействительны» (`editor-usability.js`, `editor-validity.js`).
- На 360 и 1280 px нет горизонтальной прокрутки и ошибок JS; тёмная тема не сломана.
- Тексты интерфейса — через строки (`<prefix>_t`), а не зашиты в разметку; работают на всех языках.
- README обновлён (раздел «где что править»), если поменялось, как владелец работает с сайтом.
- Нет ответа в брифе — вопрос владельцу «вопрос · варианты · влияние · рекомендация», решение — в `docs/decisions.md`.
- Коммит: Conventional Commits, тело — что и почему (см. `references/13-workflow.md`).

## Чего не делать

- Не править файлы темы и плагина на сервере (SFTP): следующий деплой их перезапишет.
- Не менять шаблоны в «Внешний вид → Редактор»: шаблон из базы перекрывает файл из git.
- Не запускать перезапись контента (`--force`) на боевом после запуска сайта.
- Не класть в репозиторий пароли, ключи, экспорт старого сайта, личные данные.
- Не тянуть шрифты с Google Fonts, не грузить счётчики до согласия, не ставить плагины ради одной функции.
- Не класть образцы текста в `default` атрибутов блока и не ставить H1 в текст или паттерн.
- Не обходить пределы размера комментариями `phpcs:ignore`/`eslint-disable` и не заводить файлы `helpers`/`utils`.
- Не включать принудительный показ шаблона в редакторе для всех записей и не делать липких элементов мимо `.acme-is-sticky`.
- Не делать статические (save) блоки для разметки, которая может меняться: старая разметка в базе станет
  «недействительной». Динамический блок перерисовывается сервером всегда.
